Casos de uso

Incluimos los cinco casos de uso mínimos que pide la consigna (iniciar pago, autorizar o rechazar, consultar, reembolsar y listar pagos) y sumamos casos de uso complementarios para completar el ciclo funcional del módulo. Cada CU referencia sus reglas, secuencia, servicio, API, DTO y entidades; la matriz maestra de trazabilidad los reúne en una sola tabla.

CU-01. Iniciar pago

IDCU-01
NombreIniciar pago
Actor principalServicio de Pedidos
ObjetivoRegistrar un intento de pago válido y único para un pedido y resolverlo con la autorización simulada.
PrecondicionesEl pedido existe y está pendiente de pago (estado BORRADOR). El usuario está activo y el medio de pago le pertenece y está activo. Pedidos envía un JWT de servicio con permiso de escritura.
Flujo principal
  1. Pedidos envía un POST a /api/v1/payments con el código de pedido, el código de usuario, el código del medio de pago, el monto, la moneda y la clave de control (DTO-01).
  2. Pagos revisa si esa clave de control ya se usó antes (RN-01).
  3. Pagos consulta al Servicio de Usuarios que el usuario exista y esté activo (INT-02).
  4. Pagos verifica que el medio de pago exista, esté activo y pertenezca al usuario.
  5. Pagos consulta a Pedidos el estado y el total del pedido (INT-01) y verifica que el monto coincida exactamente (RN-02).
  6. Pagos crea el pago en estado PENDIENTE y registra el alta en el historial (RN-09).
  7. Pagos sortea el resultado de la autorización (RN-11): el pago pasa a APROBADO, RECHAZADO, NO_AUTORIZADO o ERROR, con su motivo, y el cambio queda en el historial (RN-04, RN-09).
  8. Con el cambio ya confirmado en la base, Pagos le avisa el resultado a Pedidos (INT-04) y le pide a Notificaciones el comprobante o el aviso (INT-03).
  9. Pagos responde 201 Created con el pago, su estado y su motivo (DTO-02) y el header Location.
Flujo alternativo

2a. Si la clave ya se usó con los mismos datos, responde 200 OK con el pago existente, sin crear otro ni volver a sortear (RN-01, RN-05).

2b. Si la clave ya se usó con datos distintos, responde 409 DUPLICATE_PAYMENT_REQUEST.

3a. Si el usuario no existe o está inactivo, responde 422 PAYMENT_USER_INVALID.

4a. Si el medio de pago no existe, está inactivo o es de otro usuario, responde 422 PAYMENT_METHOD_INVALID.

5a. Si el pedido no existe o no está pendiente de pago, responde 422 ORDER_NOT_PAYABLE.

5b. Si el monto no coincide, responde 422 PAYMENT_AMOUNT_MISMATCH.

5c. Si Pedidos o Usuarios no responden, responde 503 EXTERNAL_SERVICE_UNAVAILABLE y no se crea el pago.

7a. En modo manual (autorización automática desactivada) no hay sorteo: el pago queda PENDIENTE hasta CU-02 o CU-03.

8a. Si el aviso a Pedidos o Notificaciones falla, el pago no cambia y el error se registra en el log.

ResultadoQueda creado un pago ya resuelto: APROBADO, RECHAZADO, NO_AUTORIZADO o ERROR. Si no quedó APROBADO, Pedidos puede reintentar con otra clave de control (RN-05).
RN asociadasRN-01, RN-02, RN-04, RN-05, RN-08, RN-09, RN-11
Entidades / relacionesENT-01 Pago, ENT-03 MedioPago, ENT-04 HistorialEstadoPago / REL-02, REL-03
SecuenciaSEC-01
ServicioSRV-01 PagoService.iniciarPago(), SRV-10 AutorizadorSimulado.sortear()
API / DTOAPI-01 POST /api/v1/payments / DTO-01, DTO-02

CU-02. Autorizar pago (modo manual)

IDCU-02
NombreAutorizar pago
Actor principalServicio de Pedidos (simula la respuesta de la pasarela)
ObjetivoAprobar a mano un pago pendiente. Solo hace falta en modo manual: con el sorteo activo el pago ya sale resuelto de CU-01.
PrecondicionesEl pago existe. Pedidos envía un JWT de servicio con permiso de escritura.
Flujo principal
  1. Pedidos envía un PATCH a /api/v1/payments/{codigoPago}/approve.
  2. Pagos busca el pago por su código público.
  3. Pagos verifica que el pago esté en estado PENDIENTE.
  4. El pago pasa a APROBADO (RN-04) y se registra el cambio en el historial (RN-09).
  5. Después del commit, Pagos le avisa a Pedidos (INT-04) y le pide a Notificaciones el comprobante (INT-03).
  6. Pagos responde 200 OK con el pago en estado APROBADO (DTO-02). Con esa respuesta, Pedidos confirma el pedido (RN-03).
Flujo alternativo

2a. Si el pago no existe, responde 404 PAYMENT_NOT_FOUND.

3a. Si el pago ya está APROBADO, responde 200 OK con el pago sin modificarlo (RN-10).

3b. Si el pago está RECHAZADO, NO_AUTORIZADO, en ERROR o REEMBOLSADO, responde 409 PAYMENT_INVALID_STATE (RN-04).

5a. Si Pedidos o Notificaciones no responden, el pago queda aprobado igual y el error se registra en el log.

ResultadoEl pago queda en estado APROBADO, con el historial actualizado.
RN asociadasRN-03, RN-04, RN-09, RN-10
Entidades / relacionesENT-01 Pago, ENT-04 HistorialEstadoPago / REL-03
SecuenciaSEC-02
ServicioSRV-02 PagoService.aprobarPago()
API / DTOAPI-02 PATCH /api/v1/payments/{codigoPago}/approve / DTO-02

CU-03. Rechazar pago (modo manual)

IDCU-03
NombreRechazar pago
Actor principalServicio de Pedidos (simula la respuesta de la pasarela)
ObjetivoRechazar a mano un pago pendiente, dejando registrado el motivo. Solo hace falta en modo manual.
PrecondicionesEl pago existe. Pedidos envía un JWT de servicio con permiso de escritura.
Flujo principal
  1. Pedidos envía un PATCH a /api/v1/payments/{codigoPago}/reject con el motivo del rechazo (DTO-03).
  2. Pagos busca el pago por su código público.
  3. Pagos verifica que el pago esté en estado PENDIENTE.
  4. El pago pasa a RECHAZADO (RN-04) y se registra el cambio en el historial con el motivo (RN-09).
  5. Después del commit, Pagos le avisa a Pedidos (INT-04) y le pide a Notificaciones el aviso de rechazo (INT-03).
  6. Pagos responde 200 OK con el pago en estado RECHAZADO (DTO-02). El pedido no avanza (RN-03).
Flujo alternativo

2a. Si el pago no existe, responde 404 PAYMENT_NOT_FOUND.

3a. Si el pago ya está RECHAZADO, responde 200 OK con el pago sin modificarlo (RN-10).

3b. Si el pago está APROBADO, NO_AUTORIZADO, en ERROR o REEMBOLSADO, responde 409 PAYMENT_INVALID_STATE (RN-04).

ResultadoEl pago queda en estado RECHAZADO, con el historial actualizado. Para reintentar, Pedidos envía un pago nuevo con otra clave de control (RN-05).
RN asociadasRN-03, RN-04, RN-05, RN-09, RN-10
Entidades / relacionesENT-01 Pago, ENT-04 HistorialEstadoPago / REL-03

CU-04. Consultar pago

IDCU-04
NombreConsultar pago
Actor principalPortal Web (cliente), Servicio de Pedidos o Administrador
ObjetivoConsultar el estado actual, el motivo, el monto y el medio de pago de un pago por su código público.
PrecondicionesEl actor está autenticado y cuenta con el código del pago que quiere consultar.
Flujo principal
  1. El actor hace un GET a /api/v1/payments/{codigoPago}.
  2. Pagos busca el registro por su código público, nunca por el identificador interno.
  3. Si el actor tiene rol CLIENTE, Pagos verifica que el pago le pertenezca, comparando el código de usuario del JWT.
  4. Pagos responde 200 OK con el estado actual, el motivo, el monto y el medio de pago enmascarado (DTO-02).
Flujo alternativo

2a. Si el código de pago no existe, responde 404 PAYMENT_NOT_FOUND.

3a. Si el pago es de otro usuario, responde 403 FORBIDDEN.

ResultadoQuien consulta obtiene el estado actualizado del pago.

Entidades / relacionesENT-01 Pago, ENT-03 MedioPago / REL-02
SecuenciaSEC-04

CU-05. Reembolsar pago

IDCU-05
NombreReembolsar pago
Actor principalServicio de Pedidos (cancelación del pedido) o Administrador
ObjetivoDevolver total o parcialmente un pago aprobado.
PrecondicionesEl pago existe. El actor tiene permiso de escritura.
Flujo principal
  1. Se envía un POST a /api/v1/payments/{codigoPago}/refund con el monto, el motivo y una clave de control del reembolso (DTO-04).
  2. Pagos busca el pago por su código público, con bloqueo, para que dos reembolsos simultáneos se ejecuten de a uno.
  3. Pagos revisa si la clave de control del reembolso ya se usó (RN-10).
  4. Pagos verifica que el pago esté en estado APROBADO (RN-06).
  5. Pagos valida que el monto no supere lo disponible, es decir, el monto aprobado menos lo ya reembolsado (RN-07).
  6. Pagos crea el Reembolso en estado APROBADO, de forma simulada. Si con este reembolso se cubre el total, el pago pasa a REEMBOLSADO y se registra en el historial (RN-04, RN-09).
  7. Después del commit, Pagos le pide al Servicio de Notificaciones el comprobante (INT-03) y responde 201 Created (DTO-05).
Flujo alternativo

2a. Si el pago no existe, responde 404 PAYMENT_NOT_FOUND.

3a. Si la clave de control del reembolso ya se usó con los mismos datos, responde 200 OK con el reembolso existente (RN-10). Si se usó con otro monto o sobre otro pago, responde 409 DUPLICATE_PAYMENT_REQUEST.

4a. Si el pago no está APROBADO (incluye REEMBOLSADO), responde 409 PAYMENT_INVALID_STATE.

5a. Si el monto supera lo disponible, responde 422 REFUND_EXCEEDS_AMOUNT.

ResultadoQueda registrado el reembolso. Si es total, el pago pasa a REEMBOLSADO; si es parcial, el pago sigue APROBADO con menos monto disponible para reembolsar.
RN asociadasRN-04, RN-06, RN-07, RN-09, RN-10
Entidades / relacionesENT-01 Pago, ENT-02 Reembolso, ENT-04 HistorialEstadoPago / REL-01, REL-03
SecuenciaSEC-05
ServicioSRV-05 ReembolsoService.reembolsarPago()
API / DTOAPI-05 POST /api/v1/payments/{codigoPago}/refund / DTO-04, DTO-05

CU-06. Listar pagos

IDCU-06
NombreListar pagos
Actor principalAdministrador o Analista (a través de Analítica)
ObjetivoObtener un listado paginado y filtrable de pagos para auditoría y métricas.
PrecondicionesQuien consulta está autenticado con rol ADMINISTRADOR, ANALISTA o con un JWT de servicio de lectura.
Flujo principal
  1. Se envía un GET a /api/v1/payments con filtros opcionales (estado, codigoUsuario, codigoPedido, desde, hasta) y paginación (page, size, sort).
  2. Pagos consulta el repositorio aplicando esos filtros.
  3. Pagos responde 200 OK con la página de resultados (DTO-06).
Flujo alternativo

1a. Si los parámetros no son válidos, responde 400 VALIDATION_ERROR.

ResultadoSe obtiene un listado paginado de pagos según los filtros aplicados.

CU-07. Consultar pagos asociados a un pedido

IDCU-07
NombreConsultar pagos asociados a un pedido
Actor principalServicio de Pedidos o Administrador
ObjetivoRecuperar todos los intentos de pago de un pedido para reconstruir su trazabilidad.
PrecondicionesEl actor está autenticado y conoce el código del pedido.
Flujo principal
  1. Se envía un GET a /api/v1/payments?codigoPedido={codigoPedido}.
  2. Pagos filtra los pagos por el código de pedido.
  3. Pagos responde 200 OK con la lista de intentos de pago del pedido, ordenados por fecha (DTO-06). Puede haber más de uno por los reintentos (RN-05).
Flujo alternativo

2a. Si el pedido no tiene pagos, responde 200 OK con la lista vacía.

ResultadoSe obtiene la trazabilidad de los pagos del pedido. Se reutiliza el endpoint de listado con un filtro, para no chocar con GET /api/v1/payments/{codigoPago} de CU-04.

CU-08. Registrar medio de pago

IDCU-08
NombreRegistrar medio de pago
Actor principalCliente, a través del Portal Web
ObjetivoRegistrar un medio de pago simulado del usuario guardando solo un detalle enmascarado.
PrecondicionesEl usuario está autenticado con rol CLIENTE.
Flujo principal
  1. El cliente envía un POST a /api/v1/payment-methods con el tipo y el número del medio de pago (DTO-07).
  2. Pagos toma el código de usuario del JWT, no del cuerpo de la solicitud.
  3. Pagos enmascara el detalle sensible, guarda solo los últimos 4 dígitos y descarta el número completo (RN-08).
  4. Pagos crea el MedioPago activo asociado al usuario y responde 201 Created con su código (DTO-08) y el header Location.
Flujo alternativo

1a. Si falta el tipo o el número, responde 400 VALIDATION_ERROR.

1b. Si el tipo de medio de pago no es soportado o el número no es válido, responde 422 PAYMENT_METHOD_INVALID.

ResultadoEl medio de pago queda disponible para usarse en futuros pagos.

CU-09. Detectar solicitudes duplicadas mediante idempotencia

IDCU-09
NombreDetectar solicitudes duplicadas mediante idempotencia
Actor principalServicio de Pedidos
ObjetivoEvitar que una misma solicitud de pago genere más de un pago y detectar la reutilización de la clave con datos distintos.
PrecondicionesLa solicitud de pago incluye la clave de control en el campo claveControl de DTO-01.
Flujo principal
  1. Pedidos envía un POST a /api/v1/payments con la clave de control en el cuerpo.
  2. Pagos busca si existe un pago con esa clave.
  3. Si no existe, sigue el flujo de CU-01.
  4. Si existe y los datos coinciden (pedido, usuario, monto y medio de pago), devuelve el pago original con 200 OK, en el estado en que haya quedado, sin volver a sortear.
Flujo alternativo

4a. Si la clave fue usada con datos distintos, responde 409 DUPLICATE_PAYMENT_REQUEST.

4b. Si llegan dos solicitudes simultáneas con la misma clave, la restricción UNIQUE de clave_control hace fallar la segunda inserción y Pagos devuelve el pago creado por la primera.

ResultadoSe evita la creación de pagos duplicados.
RN asociadasRN-01, RN-05
Entidades / relacionesENT-01 Pago
SecuenciaSEC-01 (flujos alternativos)
ServicioSRV-01 PagoService.iniciarPago()
API / DTOAPI-01 POST /api/v1/payments / DTO-01, DTO-02

CU-11. Dar de baja medio de pago

IDCU-11
NombreDar de baja medio de pago
Actor principalCliente, a través del Portal Web
ObjetivoDesactivar un medio de pago propio para que no pueda usarse en pagos nuevos, sin borrar los pagos ya hechos con él.
PrecondicionesEl usuario está autenticado con rol CLIENTE.
Flujo principal
  1. El cliente envía un DELETE a /api/v1/payment-methods/{codigoMedioPago}.
  2. Pagos busca el medio de pago por su código público.
  3. Pagos verifica que pertenezca al usuario del JWT.
  4. Pagos lo marca como inactivo (baja lógica) y responde 204 No Content, sin cuerpo.
Flujo alternativo

2a. Si el medio de pago no existe, responde 404 PAYMENT_METHOD_NOT_FOUND.

3a. Si pertenece a otro usuario, responde 403 FORBIDDEN.

4a. Si ya estaba inactivo, responde 204 igual, sin cambios.

ResultadoEl medio de pago deja de servir para pagos nuevos (CU-01 responde 422 PAYMENT_METHOD_INVALID); los pagos previos se conservan.
RN asociadasRN-08
Entidades / relacionesENT-03 MedioPago
SecuenciaNo aplica
ServicioSRV-09 MedioPagoService.eliminarMedioPago()
API / DTOAPI-09 DELETE /api/v1/payment-methods/{codigoMedioPago} / sin cuerpo
