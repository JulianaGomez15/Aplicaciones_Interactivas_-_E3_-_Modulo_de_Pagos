Diagramas de secuencia

Diagramas de los cinco casos de uso principales. Todos siguen el mismo recorrido por capas: el JwtAuthenticationFilter valida el token, el controlador solo valida el formato (@Valid) y delega en el servicio, que aplica las reglas y lanza una PagoException cuando algo no se cumple. El GlobalExceptionHandler la traduce al error normalizado (DTO-10).

SEC-01. Iniciar pago (CU-01 y CU-09)

Incluye los tres caminos de idempotencia y el sorteo. Usuarios y Pedidos se consultan antes de abrir la transacción; el aviso a Pedidos y la notificación salen después del commit. Las rutas se muestran sin el prefijo /api/v1.

SEC-01. Iniciar pago, segunda parte: registro, sorteo y avisos

Continúa SEC-01 cuando la clave es nueva y la solicitud es válida. El sorteo decide el estado final del pago (RN-11); el aviso a Pedidos y la notificación se envían con el cambio ya confirmado en la base.

SEC-02. Autorizar pago (CU-02, modo manual)

Solo se usa con la autorización automática desactivada. Pedidos dispara la aprobación y recibe el resultado en la respuesta; con un pago APROBADO confirma el pedido.

SEC-03. Rechazar pago (CU-03, modo manual)

Repetir el rechazo sobre un pago ya RECHAZADO devuelve 200 sin cambios (RN-10).

SEC-04. Consultar pago (CU-04)

La búsqueda es siempre por el código público; un cliente solo puede ver sus propios pagos.

SEC-05. Reembolsar pago (CU-05)

Un reembolso parcial deja el pago APROBADO; solo el reembolso total lo pasa a REEMBOLSADO.

Arquitectura del módulo

Documentamos la arquitectura con el modelo C4 en tres niveles: el contexto del módulo dentro de DeliveryGo, los contenedores que lo componen y los componentes internos de la API de Pagos.

Nivel 1: Contexto

Nivel 2: Contenedores

El módulo tiene su propia base de datos y nunca accede a tablas de otros módulos. Toda la comunicación es REST con JSON y cada request, también el tráfico interno, lleva un JWT en el header Authorization: Bearer.

Nivel 3: Componentes de la API de Pagos

La API respeta la separación controller, service y repository. Los controladores no tienen reglas de negocio, las transacciones viven en la capa de servicio y solo cubren el acceso a la base (las llamadas a otros módulos quedan afuera), y los DTOs son el único formato que cruza la frontera de la API.

Seguridad y autorización por rol

Seguimos la arquitectura de seguridad definida para el TPO. El Portal Web se autentica contra la API de Usuarios, que es el único emisor de JWT. Desde ahí, cada API del ecosistema recibe el token en el header Authorization: Bearer y valida por su cuenta la firma y el rol, sin consultar a Usuarios en cada request. Las llamadas entre APIs (por ejemplo, Pedidos hacia Pagos) usan un JWT de servicio con permiso de lectura o de escritura que identifica a la API que llama.

Pagos solo consulta a Usuarios (INT-02) para una verificación de negocio: que el cliente que paga exista y esté activo. Esa consulta no reemplaza la validación del token. Si la solicitud no trae un JWT válido, responde 401 con el header WWW-Authenticate: Bearer; si el rol no tiene permiso, responde 403. Con un JWT válido, una ruta que no existe responde 404 y un método que la ruta no acepta responde 405 con el header Allow.
