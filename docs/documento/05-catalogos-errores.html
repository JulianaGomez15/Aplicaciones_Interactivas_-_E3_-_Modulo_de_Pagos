Catálogos de trazabilidad

Estos catálogos definen los identificadores que usan los casos de uso y la matriz maestra. Las entidades (ENT), relaciones (REL) y repositorios (REP) están en las secciones de DER y persistencia.

Integraciones

Todas las integraciones son sincrónicas por REST, usan un JWT de servicio, propagan el header X-Correlation-Id y tienen timeout. INT-01 e INT-02 se llaman antes de abrir la transacción; INT-03 e INT-04, después del commit. El resultado de la autorización le llega a Pedidos dos veces: en la respuesta de API-01 y en el aviso INT-04.

Manejo de errores

Todos los errores se devuelven con el formato normalizado del ecosistema (DTO-10). Lo arma un único componente (ErrorResponseFactory), que usan el GlobalExceptionHandler y el manejador de errores de seguridad, así los 401 y 403 tienen el mismo formato que el resto.

CampoDescripción
timestampFecha y hora del error, en formato ISO-8601 sin zona horaria, igual que las fechas de los pagos.
statusCódigo HTTP asociado al error.
codeCódigo de error propio del módulo, según el listado de códigos de error del módulo.
messageMensaje descriptivo pensado para quien consume la API.
pathEndpoint donde ocurrió el error.
correlationIdIdentificador de correlación, tomado del header X-Correlation-Id (o generado si no vino), que sirve para seguir el rastro entre módulos.

Decisiones técnicas

IDDecisión
DEC-01Cada tabla tiene un id interno bigint, que no se expone, y un código UUID único que es el que se usa en la API y en las referencias a otros módulos.
DEC-02La clave de control viaja en el cuerpo de la solicitud (claveControl) y tiene restricción UNIQUE, que también cubre solicitudes simultáneas.
DEC-03La autorización es simulada y la resuelve Pagos con un sorteo al iniciar el pago (RN-11). El resultado vuelve en la respuesta de API-01 y además Pagos se lo avisa a Pedidos (INT-04). Aprobar y rechazar a mano quedan para el modo manual (autorizacion.automatica=false).
DEC-04Usuarios es el único emisor de JWT. Pagos valida localmente la firma y el rol en cada request; entre APIs se usa un JWT de servicio.
DEC-05Pago usa bloqueo optimista (@Version) para que dos operaciones simultáneas sobre el mismo pago no generen dos transiciones. Los reembolsos además leen el pago con bloqueo de escritura.
DEC-06Los estados y tipos se modelan como enums y se persisten con @Enumerated(STRING). Los montos usan BigDecimal y numeric(12,2).
DEC-07Todas las relaciones son LAZY. Cuando hace falta el medio de pago se usa una consulta con fetch join, para evitar el problema N+1.
DEC-08Si Notificaciones o el aviso a Pedidos fallan, la operación de pago no se revierte; el error queda registrado en el log.
DEC-09Los controladores implementan interfaces (IPagoController, IMedioPagoController) con las anotaciones de OpenAPI y no tienen reglas de negocio.
DEC-10Las llamadas HTTP a otros módulos nunca se hacen con la transacción abierta: Usuarios y Pedidos se consultan antes, y el aviso a Pedidos y la notificación se envían después del commit. La base solo queda tomada para el alta del pago y para el cambio de estado.
DEC-11La base es H2 en memoria: cada arranque empieza limpio y carga datos de demo. El diseño original preveía PostgreSQL con docker-compose; el equipo decidió mantener H2 para simplificar la ejecución.
DEC-12Mientras no esté integrado el Servicio de Usuarios, hay un único usuario de demo (demo / demo123) con todos los roles, que simula la emisión del JWT. Las reglas de rol por endpoint no cambian.
DEC-13Cada operación imprime en la consola un bloque con un renglón por paso (solicitud, validaciones, registro, sorteo, aviso a Pedidos, notificación y resultado), para mostrar el flujo en la presentación.
DEC-14Los estados NO_AUTORIZADO y ERROR son finales, igual que RECHAZADO: el pago queda registrado para auditoría y el reintento se hace con una clave de control nueva. Por eso API-01 responde 201 aunque el pago no quede aprobado: el resultado de negocio va en el cuerpo (estado y motivo).
DEC-15Las rutas sin regla de rol exigen estar autenticado en lugar de denegarse siempre, para que una ruta o un método equivocados respondan 404 o 405 y no 403.
